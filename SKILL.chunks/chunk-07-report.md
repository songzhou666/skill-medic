# Chunk 07：报告生成

> 加载条件：`phase == MED_DEBRIEF`

## 报告结构（元信息 + 9 个部分，双层：编号 1 人话汇报层 + 编号 2~9 专业明细层）

> 报告面向**普通用户**：编号 1 是"人话汇报层"（结论先给，大白话），编号 2~9 是"专业明细层"
> （专业数据与证据完整保留，需要深究的用户继续往下看）。专业术语（C1~C5 / L0~L3 / 八维）作为括号备注，
> 主表达用日常语言。报告标题统一为 **"Skill 检查报告"**。

```
# Skill 检查报告
0. 元信息：检查时间 / 扫描范围 / 评分标准版本 / 异常 Skill（损坏）清单
0.1 怎么读这份报告（图例，普通用户先看这里）——**固定区块，07-reporter 重写报告时不得删减**：
   - 结论在前：第 1 部分是人话总结，第 2~9 部分是专业明细，看不懂细节不影响拿结论
   - 四档评级（**衡量可靠性/完成度，不是安不安全**）：放心用（L3）= 能稳定完成功能、出问题能自己兜住；
     基本能用（L2）= 常规场景能完成，但缺异常处理，复杂输入可能出错；不太成熟（L1）= 只能处理理想样例，
     真实业务容易翻车；不建议用（L0）= 基本不可用
   - 冲突类型：功能重复（C1）/ 抢着响应（C2）/ 占资源（C3）/ 共享依赖（C4）/ 抢工具（C5）含义一句话
   - 八维评分与严重度说明
   - **对号入座**：只是用 Skill 干活 → 看第 1 部分和第 7.1；自己写/维护 Skill → 看第 7.2
1. 给你的结论（人话版汇报层，LLM 回填，必写）
   - 1.1 健康度总评：一句话总评 + 分布条（放心用 █ 7 ｜ 基本能用 █ 5 ｜ 不太成熟 █ 1 ｜ 不建议用 █ 1）
     + **分级名单（逐个点名）**：列出每个 Skill 的名字并归入四档
     （放心用 L3 / 基本能用 L2 / 不太成熟 L1 / 不建议用 L0），没有则写"无"；
     例：放心用（L3）：示例 Skill A、示例 Skill B；不太成熟（L1）：示例 Skill C —— 让"谁好谁不好"落到具体名字
     + **使用局限**：对"不太成熟 / 不建议用"档的 Skill，各补一句"什么场景下容易出问题、别用它做什么"
       （例："示例 Skill C 只适合演示，处理真实业务文档容易出错，别用在正式项目"）
   - 1.2 最需要注意的问题 TOP 榜（3~5 条）：问题一句话 / 影响你什么 / 建议怎么办（建议必须是**使用类**，如"以后都用 A"）
   - 1.3 你现在最该做的 2~3 件事（**如果你是使用者**，只给不用改文件的使用类建议；创建者想改文件的看 7.2）
   - 铁律：汇报层数据**必须**从第 5 部分冲突、第 6 部分评分、第 7.1 使用建议推导，禁止另写一套分布（05-auditor BLOCK-E 核对）
2. 总览
   - Skill 总数 / 活跃/异常 / token 平均与最大 / 功能域分布（静态提示）
   - 健康度分布条（LLM 回填，与第 1.1 节、第 6 部分一致）
3. 清单表（MED_ROSTER）：Skill / 状态（正常|损坏）/ 所在位置（项目内|全局）/ token / 版本 / 结构(多角色/分块/工具/协议)
4. 分类表（MED_SORT）：用途分组 / 交互方式 / 维护状态（domain_final 由 LLM 回填）
5. 冲突与问题（MED_CONFLICT，专业明细层）
   - 冲突类型列用通俗名 + 括号编号：功能重复（C1）/ 抢着响应（C2）/ 占资源（C3）/ 共享依赖（C4）/ 抢工具（C5）
   - 严重度列：待确认 / 低 / 中 / 高（candidate 映射为"待确认"）
   - 每个冲突/问题包含 5 列：A×B / 冲突类型 / 冲突点·资源 / 初判严重度 / 影响你什么（回填）
   - 影响必须说人话，例如：
     - C2 意图抢占："当你说'帮我扫描页面'时，有 2 个 Skill 都会响应，AI 可能随机选一个 → 结果不稳定"
     - C1 重复："两个 Skill 做同一件事，你不知道该用哪个，建议只留一个"
     - 重复安装："发现同一 Skill 在两个 IDE 的目录里各装了一份（如 Trae 和 Claude）→ 是因为你分别安装过，建议只保留一份"
     - C3 膨胀："这个 Skill 每次对话都要加载约 7000 字说明，比较占资源，可能拖慢 AI 响应"
   - C4_infra 共享聚合单列
6. 评分明细（MED_VITAL）：列名通俗化（触发说明/流程步骤/异常处理/产出检查/边界约束/工程配套/维护痕迹），
   数字 = 机器统计证据数（专业参考），最后一列"通俗评估"由 LLM 回填，定级**必须**用"放心用（L3）"格式；
   "内容价值"维度由 AI 语义评判，不在表中
7. 行动建议（按角色对号入座）
   - **7.1 使用建议**（LLM 回填）——**如果你是 Skill 的使用者，看这里**：不用改文件，覆盖"注意什么 / 有什么风险 / 什么需求别指望它"
   - **7.2 改造建议**（规则候选）——**如果你是 Skill 的创建者 / 维护者，看这里**：需修改 Skill 文件
     （合并重复/补'何时不要调用'/划清边界/明确分工顺序/瘦身/补维护文档），标注"使用者可完全跳过本节"；
     表格含**优先级列（高/中/低，按严重度排序）**，每条 = 优先级 / 建议方向 / 对象 / 依据 / 精确操作（文件路径+改动内容+执行方式）
8. 历史对比：与上次清单 diff（新增/消失）；"上次的问题解决了吗"由 LLM 补充
9. 标准对照表：当前 rubric 版本 + 联网更新记录；
   **定级规则必须引用 chunk-05 固定阈值（L3≥80 / L2 55~79 / L1 30~54 / L0<30），禁止自创阈值**（05-auditor BLOCK-E 核对）
```

## 输出动作

- 强制 `medic_tools/run.py report` 落盘 `.medic/skill_audit_report_{时间戳}.md`（目录自动创建）
- 同时落盘 `.medic/_medic_inventory.json`（本次清单）；**把旧清单归档为 `.medic/_medic_last_inventory.json`**
  （增量 diff / 历史对比的单一数据源，report 与 diff 都读它）
- 主回复内同步输出完整报告（Markdown）
- 不写数据库

## LLM 回填区（07-reporter 职责）

> **报告正文零场外话铁律（强约束）**：报告是给用户看的**成品**，不是 AI 的工作底稿。
> 回填时必须：① 把模板中的全部 HTML 注释（`<!-- ... -->`）替换为真实内容后**删除**；
> ② 补全 1.1 分级名单、1.2/1.3、白话导读、7.1 使用建议等空占位；③ 最终报告正文**不得残留**
> "例：/LLM 回填/AI 回填/回填区"等任何模板指导语，也不得残留未替换的"（）"空占位。

报告装配后，07-reporter 必须回填：
1. **第 1 部分汇报层（人话版，必写）**：
   - 1.1 健康度总评：一句话总评 + 分布条 —— **必须从第 6 部分评分表定级汇总推导**，禁止另写一套分布；
     **分级名单**逐个点名归入四档；对"不太成熟 / 不建议用"档的 Skill 各补一句**使用局限**
     （"什么场景下容易出问题、别用它做什么"）
   - 1.2 TOP 问题榜 3~5 条：每条 = 问题一句话 / 影响你什么 / 建议怎么办（建议必须是**使用类**，从第 5 部分冲突矩阵挑选）
   - 1.3 最该做的 2~3 件事（**如果你是使用者**）：从 **7.1 使用建议**中挑优先级最高的（**只给不用改文件的**），写成可执行的一句话动作
2. **7.1 使用建议（必写）——面向"使用者"**：从评分/冲突推导，覆盖"注意什么 / 有什么风险 / 什么需求别指望它"，
   每条都是不用改文件、直接照做的操作（例："别用 XX 处理正式数据"）
3. **评分明细**：对照八维细则，每 Skill 给分 + 证据 + 扣分定位（文件/章节）+ L0~L3 定级
4. **历史洞察**：成熟度变化、冲突新增与缓解、上期处方执行核对（AI 自主发现趋势/异常/机会点，不限制格式）
5. **7.2 改造建议精确操作——面向"创建者 / 维护者"**：为每条改造建议补文件路径 + 改动内容 + 执行方式 + 优先级
   （标注"使用者可完全跳过本节"）
6. **冲突影响**：每个冲突补"影响你什么"（日常语言 + 自然语言唤醒举例）；高严重度冲突（严重度=高/中）必须回填

> 回填内容为 LLM 智能分析层（软约束）：只约束要素，不约束表述与深度。
> 汇报层（第 1 部分）与明细层（第 5/6/7 部分）是"结论 ↔ 证据"关系：结论可简化、不可矛盾。
